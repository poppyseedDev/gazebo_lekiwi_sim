# LeKiwi Simulation Project — Handoff

A summary of the project goal, decisions made, current state, and what's next. Hand this to Claude Code (or any new Claude session) on the VM to pick up where we left off.

## The goal

Build a Gazebo Harmonic simulation of a **LeKiwi mobile manipulator** (3-wheel omnidirectional base from SIGRobotics-UIUC, with a LiDAR and an SO-101 arm), running ROS 2 Jazzy on Ubuntu 24.04 ARM64, ultimately driving it autonomously with Nav2. The physical robot is a Raspberry Pi 5-based platform from the LeRobot/Hugging Face ecosystem.

The simulation work happens on a Mac (Apple Silicon) inside a UTM Linux VM. The real robot deployment runs on the Pi. Code structure is shared between sim and real where possible; only bringup launch files differ.

## Hardware being simulated

- **Base**: LeKiwi — 3 omni wheels at 120°, kiwi-drive kinematics, holonomic
- **Sensors**: 2D LiDAR (LD19) mounted above the Pi
- **Arm**: SO-101 6-DoF (treated as static visual for now, no manipulation simulation)

## Key decisions and rationale

- **ROS 2 Jazzy** (not Kilted/Humble): LTS, supported until May 2029, current best choice
- **Gazebo Harmonic** (not Classic, not Isaac, not MuJoCo): Classic is EOL, Harmonic is the standard ROS 2 sim, MuJoCo is for manipulation policy work which isn't the focus
- **UTM with Apple Virtualization**, hardware OpenGL on, Rosetta off: works well enough for Gazebo on Apple Silicon
- **XFCE desktop** (not GNOME): lighter, snappier in a VM
- **Don't run Gazebo on the Pi**: Pi handles real-robot deployment only
- **Build on Aditya Kamath's `lekiwi_ros2`** instead of authoring URDF from scratch: he's already done the URDF and ros2_control config; we add Gazebo on top
- **Skip Docker for sim work**: GPU passthrough + GUI forwarding on Mac via Docker is painful; native Linux VM is cleaner
- **Use `omni_wheel_drive_controller`** (from ros2_controllers) for kiwi-drive — correct controller for 3-wheel omni; planar-move plugin is a faster shortcut for early testing
- **Three-package split**: `*_description` shared sim+real, `*_gazebo` sim-only, `*_navigation` shared sim+real, `*_control` real-only, `*_bringup` per-target

## The plan from here, in phases

### Phase A: confirm the description package works (next step)

Verify the URDF visualizes correctly in RViz before touching Gazebo. Find the description package's launch files:

```bash
ls ~/lekiwi_ws/src/lekiwi_ros2/lekiwi_description/launch/
```

Run whichever launch file does display/RViz/rsp. Expected outcome: RViz opens, shows the LeKiwi 3D model with three omni wheels, base, LiDAR mount, camera mount. A `joint_state_publisher_gui` window with sliders may also appear; moving sliders should rotate wheels.

Common issues:
- Missing meshes (mesh path resolution) — fix mesh paths in URDF, often `package://` references
- TF errors — usually missing static frame setup in launch file
- `xacro` not found — `sudo apt install ros-jazzy-xacro`

### Phase B: add Gazebo simulation glue

Aditya's repo doesn't include Gazebo bits. Create a new `lekiwi_gazebo` package alongside the others:

```bash
cd ~/lekiwi_ws/src
ros2 pkg create --build-type ament_python --license Apache-2.0 lekiwi_gazebo \
  --dependencies ros_gz_sim ros_gz_bridge robot_state_publisher xacro
```

What it needs to contain:
- `worlds/empty.world` or use stock `empty.sdf` from ros_gz
- `config/ros_gz_bridge.yaml` for `/clock`, `/cmd_vel`, `/scan`, `/odom`, `/tf`, `/imu`
- `launch/sim_bringup.launch.py` that:
  1. Starts Gazebo (`IncludeLaunchDescription` of `gz_sim.launch.py` with world arg)
  2. Starts `robot_state_publisher` reading the URDF (set `use_sim_time:=true`)
  3. Spawns the robot via `ros_gz_sim create -topic robot_description`
  4. Starts `parameter_bridge` from the YAML config

What the URDF needs added (probably as a Xacro include in a new file `lekiwi.gazebo.xacro` so the description package stays sim/real-shared):
- `<gazebo>` block on the LiDAR link with a `gpu_lidar` sensor
- A drive plugin — start with `gz::sim::systems::PlanarMove` for fast iteration; replace with `gz_ros2_control` + `omni_wheel_drive_controller` once everything else works
- World system plugins (Physics, UserCommands, SceneBroadcaster, Sensors, Imu)

The skill on this Claude session covers all these patterns in detail — look for `references/gazebo.md` if continuing in a context that has the skill loaded.

### Phase C: SLAM in sim

Once the robot drives in Gazebo and `/scan`, `/odom`, and `/tf` are correct:

```bash
ros2 launch slam_toolbox online_async_launch.py use_sim_time:=true
```

Drive around with teleop. If the map looks coherent, the simulation is solid. If garbage, debug TF or sensor placement before going further.

Save the map:

```bash
ros2 service call /slam_toolbox/save_map slam_toolbox/srv/SaveMap "{name: {data: 'office'}}"
ros2 run nav2_map_server map_saver_cli -f ~/lekiwi_ws/src/lekiwi_navigation/maps/office
```

### Phase D: Nav2 against the saved map

Create `lekiwi_navigation` package:

```bash
cd ~/lekiwi_ws/src
ros2 pkg create --build-type ament_python --license Apache-2.0 lekiwi_navigation \
  --dependencies nav2_bringup nav2_common slam_toolbox
```

Copy `nav2_bringup`'s param yaml as a starting point. Notes for Jazzy specifically:
- Use `error_code_name_prefixes` not the deprecated `error_code_names`
- `static_layer.map_topic` lives inside the static_layer block, not on the costmap
- `NavigateThroughPoses` uses `nav_msgs/Goals` (with header) — access via `.goals.goals`
- For omni-drive, MPPI controller with holonomic mode is the recommended controller

### Phase E: real-robot deployment

Different bringup launch file pointing at real LiDAR (`ldlidar_ros2`) + STS3215 driver instead of Gazebo. Same `lekiwi_description` and `lekiwi_navigation`. Flip `use_sim_time:=false`.

### Phase F: SO-101 arm as static include

Pull URDF from `TheRobotStudio/SO-ARM100`. Include via Xacro into the LeKiwi base description. No controller, no plugin — just for footprint and visual realism.

## Watch out for

- Aditya's repo targets Kilted; built fine on Jazzy but watch for runtime API differences if errors appear
- Aditya uses Zenoh RMW for laptop↔Pi comms; not required, default Fast DDS is fine in sim
- The kiwi-drive controller is `omni_wheel_drive_controller` — not the more commonly-cited mecanum or diff drive
- Gazebo Harmonic uses `gz` commands, not `ign` (old Ignition) or `gazebo` (Classic)
- Jazzy-specific Nav2 migrations matter: the `error_code_name_prefixes` rename, `nav_msgs/Goals`, etc.
- Gazebo on Apple Silicon UTM may need OGRE 1 fallback if OGRE 2 misbehaves: `gz_args:='--render-engine ogre -r ...'`
